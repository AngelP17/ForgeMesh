# AGENTS.md

Guidance for Codex sessions working in this repo. Read this before planning or editing.

## Project Snapshot

Vigil is a local-first operational incident intelligence platform. It evolved from ForgeMesh and keeps the original industrial data substrate: Rust ingestion, Sled-backed telemetry chains, Merkle-DAG replay, Axum delivery, and optional peer sync. Vigil adds incident state, operator actions, replay/audit surfaces, a read-first copilot, and a React operations workbench.

Primary workflow:

```text
Ingest -> Detect -> Explain -> Recommend -> Act -> Replay
```

## Repo Map

- `crates/vigil-core/` - storage, simulation, analytics, rules, incidents, auth, exports, replay, and copilot logic.
- `crates/vigil-cli/` - `vigil` CLI entrypoint for seeding, detection, daemon, verification, import/export, user creation, and demo flows.
- `crates/vigil-web/` - Axum API, static asset serving, dashboard HTML/static bundle, PDF/report helpers.
- `crates/vigil-sync/` - CAR import/export and delta sync helpers.
- `crates/vigil-p2p/` - CRDT and gossip mesh support.
- `apps/web/` - Vite + React + TypeScript frontend source.
- `migrations/` - SQLite schema migrations used by the backend.
- `data/` - demo/sample machine logs, tickets, and operator notes.
- `demo/` - demo script, scenario notes, and screenshot capture tooling.
- `scripts/` - shell helpers for demo seeding and local demo flow.

## Setup

Required:

- Rust toolchain compatible with the workspace. The README says Rust 1.75+, while the Dockerfile currently uses Rust 1.86.
- SQLite available locally.
- Node.js and npm for `apps/web` and screenshot tooling.
- `just` is optional, but the repo includes a `Justfile`.

Install/fetch dependencies:

```bash
cargo fetch
cd apps/web && npm install
```

## Backend Commands

From the repo root:

```bash
cargo build
cargo build --release
cargo check --all-features
cargo test --workspace
cargo run -p vigil-cli -- seed-demo
cargo run -p vigil-cli -- detect
cargo run -p vigil-cli -- daemon --port 8080
cargo run -p vigil-cli -- verify -s ontario-line1-temp
```

Equivalent `just` recipes where available:

```bash
just setup
just build
just test
just seed-demo
just detect
just daemon
just sample
just export-test
```

The daemon seeds demo data and runs the incident pipeline on startup, then serves the UI at `http://localhost:8080`.

## Frontend Commands

From `apps/web/`:

```bash
npm install
npm run dev
npm run build
npm run lint
npm run preview
```

The production frontend build emits `apps/web/dist/`. Built assets are copied into `crates/vigil-web/static/` when preparing the Axum-served UI. Do not hand-edit generated bundles.

## Docker

From the repo root:

```bash
docker compose up --build
```

The service exposes port `8080` and stores runtime data in the `vigil-data` Docker volume.

## Tests and Verification

Run the smallest relevant checks for the files touched. Prefer:

```bash
cargo fmt --check
cargo check --all-features
cargo test --workspace
cd apps/web && npm run lint
cd apps/web && npm run build
```

CI currently runs:

```bash
cargo check --all-features
cargo test
```

For screenshot verification, start the daemon in one terminal:

```bash
cargo run -p vigil-cli -- daemon --port 8080
```

Then run from `demo/screenshots/`:

```bash
npm install
npx playwright install chromium
VIGIL_BASE_URL=http://127.0.0.1:8080 node capture.mjs
node capture-landing.mjs
```

## Runtime Data and Generated Files

Avoid editing these unless the task explicitly asks for generated output or fixture changes:

- `target/`
- `apps/web/node_modules/`
- `apps/web/dist/`
- `demo/screenshots/node_modules/`
- `crates/vigil-web/static/` generated frontend assets
- `vigil_data/`
- `backup.car`
- local SQLite/Sled runtime data

Treat `data/sample_machine_logs.jsonl`, `data/sample_maintenance_tickets.csv`, and `data/sample_operator_notes.jsonl` as demo fixtures. They may be regenerated by seeding scripts, so check the worktree before changing or reverting them.

## Backend Conventions

- Preserve the local-first, zero-required-SaaS product goal.
- Keep the Sled telemetry chain and SQLite operational state split unless a task explicitly changes storage architecture.
- v1 incident rules are intentionally narrow: `temp_spike`, `vibration_anomaly`, and `multi_machine_cascade`.
- Keep copilot behavior read-only. It may summarize, explain, prepare handoff text, and answer bounded questions, but it must not mutate operational state.
- Preserve the replay verification literal from `crates/vigil-core/src/audit.rs`: `Valid Merkle path - data untampered`.
- Auth-related behavior is controlled by `VIGIL_REQUIRE_AUTH` and `VIGIL_ENFORCE_TENANT_SCOPE`; do not silently weaken protected write/action paths.
- Optional Slack integration must remain optional. Core detection, replay, and dashboard flows should work without external services.

## Frontend Conventions

The current frontend is Vite + React + TypeScript + Tailwind v3, using Geist fonts, Chart.js, GSAP, and `lucide-react`. Do not migrate Tailwind, icon systems, routers, or animation libraries unless the task explicitly requires it.

For marketing or redesign surfaces, apply the `design-taste-frontend` skill as an audit-first process:

- Detect whether the task is preserve, overhaul, or greenfield before changing visuals.
- Keep the product audience in mind: operational, security-conscious, industrial supervisors and technical reviewers.
- Maintain a serious industrial/devtool language. Avoid generic AI-purple gradients, fake dashboards, decorative version labels, unnecessary scroll cues, and invented precision.
- Use real product screenshots or generated assets for marketing visuals. Do not build fake screenshot panels from decorative divs unless they are actual live component previews.
- Respect reduced motion for GSAP or other motion work, and clean up animation effects.
- Keep navigation single-line on desktop, preserve accessible focus and contrast, and test mobile collapse explicitly.

## API and Data Contracts

- Keep documented routes in `README.md` and `QUICKSTART.md` aligned with `crates/vigil-web/src/api.rs`.
- Do not rename routes, JSON fields, auth headers, or form fields without updating backend, frontend, tests, and docs together.
- If a command changes the database schema, add or update a migration in `migrations/`.
- If demo data format changes, update seeding scripts, sample files, README/quickstart references, and tests that depend on those fixtures.

## Documentation Rules

- Prefer repo-relative paths in docs.
- Document only commands that exist in manifests, scripts, CI, or source.
- When a behavior is unknown, write an `Unknowns` or `Blockers` note instead of guessing.
- Keep README-level docs user-facing. Put agent-specific constraints here.

## Done When

For code changes, a future Codex task is done when:

- The requested behavior is implemented without unrelated rewrites.
- Backend, frontend, docs, and fixtures are updated together where contracts changed.
- Relevant checks were run and results are reported.
- Any skipped check has a concrete reason.
- New runtime or setup requirements are documented.
- Generated files are either intentionally regenerated or left untouched.
- Existing user changes in the worktree are preserved.

For documentation-only changes, done means:

- Setup, build, test, lint, format, and typecheck commands are accurate where discoverable.
- Unknowns and blockers are explicit.
- Future agents can identify the project shape, quality bar, and safe verification path within a few minutes.
